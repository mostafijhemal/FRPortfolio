Small models changed where AI features live

For a few years, “add an AI feature” meant “add an API client”. That assumption is quietly breaking: a model small enough to run inside the app turns a network call into a local function, and the trade-offs move with it.

14 October 2026 · 5 min read

The interesting shift is not that small models got good in isolation. It is that the cost of a query stopped being dominated by the network and the invoice, and started being dominated by memory and battery — constraints you can reason about locally, on a machine you control.

Three things change at once

When the model runs next to your UI instead of across the internet, three properties flip at the same time.

  • Latency stops being a round trip. A local call that takes 300ms feels instant, while a 300ms API call is a spinner someone notices.
  • Cost becomes a download. You ship the weights once instead of paying per word forever — which changes which features are even worth building.
  • Privacy becomes the default. Text typed into the app never leaves the device, so the feature can be offered without a consent dialog that nobody reads.

The feature stops being a feature

This is the part I find most interesting. When the model is on-device, it behaves like any other part of the app: it can sit in a loop, run on every keystroke, or power something as small as a smarter sort order. You stop designing around a quota and start designing around what would actually help.

An offline suggestion that always answers beats a brilliant one that needs a request ID, a timeout state, and a retry button.

The trade-offs are real

I would not pretend this is free. A small model has a lower ceiling: it will fail the long, multi-step reasoning task that a hosted model handles without drama. It also has a fixed memory footprint, a slower update cycle — every improvement means shipping an app build — and it competes with the rest of your process for CPU.

In practice that means building in a fallback from the first day: a clear answer for “this needs more than I can do here”, rather than a confident wrong one.

When I still reach for a hosted model

Anything that needs a large context window, a chain of tools, or a judgement call with real consequences still belongs behind an API where I can log it, rate-limit it, and swap the model without an app release. The useful pattern is a split: small local model for the fast, private, always-available layer; hosted model for the rare, heavy request that a user explicitly makes.

That split is not a technicality. It changes where the feature lives in the product — and increasingly, the version that lives in the app is the one people actually use.
