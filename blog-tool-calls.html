Tool calls are the new API surface

A tool description is an API spec written for a reader that follows instructions instead of reading code. That one change rewrites what a good error message has to say — and who you are really designing for.

2 October 2026 · 6 min read

I have written a lot of REST endpoints where the documentation was an afterthought for a human who would read it once. Tool definitions invert that: the description is not documentation, it is the implementation of how the caller decides what to do. Get the wording wrong and the code is wrong too.

A tool description is a spec

When an agent picks a tool, it is matching your prose against its goal. “Fetch user” and “Fetch user by email, read-only” are the same function with very different failure modes. The second one tells the caller when not to use it, which is the part people leave out.

So the description earns the same care as a function signature:

  • What it does, in one sentence with no hedging.
  • When to use it, including the case it looks right for but is not.
  • What it costs — a read is free to retry, a write is not.
  • What comes back, in the shape the caller will see, not the shape your ORM produced.

Write errors for a reader, not a logger

A human reading a stack trace has context. An agent does not. It has your message and nothing else, so an error is a prompt, whether you meant it to be or not. 

{\n  "ok": false,\n  "code": "invalid_date",\n  "message": "\"2026-13-02\" is not a valid date. Use YYYY-MM-DD.",\n  "retryable": true\n}

Compare that to 400 Bad Request. One of them lets the run fix itself on the next step; the other wastes a model call guessing. The retryable flag matters just as much — nothing annoys people faster than an agent retrying a permission error four times.

Keep the surface small

Every tool you expose is another decision the model has to make, and more choices means more wrong ones. I would rather have six sharp tools than twenty overlapping ones — list_orders, get_order, and update_order_status are easier to reason about than one orders endpoint with a mode string.

If two tools could plausibly be chosen for the same request, that is a bug in the design, not a bug in the model.

What MCP-style protocols get right

Standardising how tools are described — names, JSON schemas, result shapes — means the same definition works across clients instead of being rewritten per assistant. The value is not the transport; it is that tool design becomes a reviewable artefact, like an OpenAPI file. You can diff it, test it, and notice when someone quietly widens a schema.

That is the part worth copying even if you never adopt a protocol: describe your tools in a file, keep it under version control, and treat a change to a description as a change to the API.

The work is still the work

None of this removes the need for the things APIs always needed — authentication, scoping, idempotency, rate limits. It just adds a new audience for the documentation. The tools that hold up are the ones where the description, the schema, and the error text were designed together, by someone who expected to be woken up when they went wrong.
