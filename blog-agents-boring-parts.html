AI & agents

The boring parts of AI agents are the parts that matter

The demo is the easy part. What decides whether an agent is still useful six weeks later is everything around the model: what it is allowed to touch, what happens when a step fails, and whether a human ever reads what it produced.

28 October 2026 · 7 min read

I have now watched a handful of agent demos turn into actual internal tools, and the pattern is consistent. The part that gets shared in chat — the model reading a ticket and opening a pull request — takes an afternoon. The part that makes it trustworthy takes the rest of the month, and almost none of it involves prompting.

An agent is a loop with a budget

Strip away the branding and an agent is a while loop: ask the model what to do, run the tool it picked, append the result, repeat. The engineering question is not “how do I make it smarter” but “how does this loop end”.

Every loop needs three limits, and they belong in code, not in the prompt:

  • Steps. A maximum number of tool calls before it stops and reports what it has.
  • Spend. A token or time ceiling, so one confused run cannot quietly cost a day of budget.
  • Blast radius. What the run is allowed to change, decided before it starts, not negotiated by the model mid-run.

None of that is exciting. All of it is the difference between a tool people leave running and a tool people babysit.

Permissions are the product

A tool you hand to a model is a hole in your system with a natural language front door. So the default has to be boring: read first, write later, and write only behind an explicit approval step.

If you would not give the credential to a new intern on their first morning, do not give it to an agent on its first run.

In practice that means scoped database users, separate API tokens per tool, and no shared “admin” key because it was easier to wire up. It also means the boring audit trail: which run, which tool, which arguments, which result. When something goes wrong, that log is the only thing that tells you whether the model was wrong or the tool was.

Errors are the interface

Half the perceived quality of an agent is how well it recovers from a failed tool call. A vague 500 Internal Server Error sends it guessing; a message that names the bad field sends it fixing.

Treat tool errors as copy you are writing for a very literal reader. Say what failed, which input caused it, and what a valid input looks like. The same error string is now a product decision, not just a log line.

The diff still needs a reader

Generated code is a draft from a fast, confident colleague who has never been in the codebase. That is genuinely useful and genuinely incomplete. The workflow that has held up for me is small diffs, a test that fails before the change and passes after, and a human who reads every line before merge — not because the model is untrustworthy, but because a reviewer who skims is how subtle bugs get in regardless of who wrote the code.

What this changed in how I build

I spend far less time on prompts and far more on the scaffolding around them: smaller, sharper tools; structured results; a dry-run mode for anything that writes; and a summary at the end that says what changed instead of what the model was thinking.

The impressive part of an agent is the demo. The useful part is the plumbing — and the plumbing is where I would spend my next month too.
